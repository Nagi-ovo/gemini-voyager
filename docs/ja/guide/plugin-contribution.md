# プラグイン貢献ガイド

Voyager のプラグインシステムは、宣言的なプラグインを中心に設計されています。プラグインのメタデータと DOM 操作は `plugin.json` に記述し、見た目の変更は CSS に記述します。プラグインがリモートの JavaScript を実行することはありません。Voyager に内蔵されたプラグインエンジンが、マニフェストとスタイルを解釈します。

そのため、プラグインのレビューと保守がしやすくなります。プラグインを貢献したい場合は、まずこのページから始めてください。

## 自分だけで使う場合: ローカルプラグイン

自分のブラウザだけで使うプラグインであれば、この手順は必要ありません。ローカルプラグインとして作成し、ポップアップからインポートしてください。Issue も PR もリポジトリのチェックアウトも不要です。[独自のプラグインを作る](./write-a-plugin.md) では、3 つの作成方法を説明しています。`create-voyager-plugin` のチェッカーと、コーディングエージェント向けのスキルも含まれます。

## 推奨の手順

1. アイデアがプラグイン向きか確認します。読みやすさの幅、レイアウトの修正、テーマの調整、ページ要素の非表示やマーク、簡単なサイトへの対応などは、通常よい候補です。
2. まず Voyager リポジトリで Issue を作成し、解決したい問題、対象のウェブサイト、既存のプラグインとの違いを説明します。メンテナーが明示的に承認するまで、コーディングや PR の作成は待ってください。
3. `plugin.json` に、メタデータ、対象サイト、設定、貢献内容（`contributes`）を書きます。
4. スタイルは同じプラグインディレクトリの `style.css` に書き、`contributes.styles` から参照します。
5. ローカルでテストし、テストページ、スクリーンショット、または短い録画を PR に含めます。公式カタログに入れるかどうかは、メンテナーが判断します。

## ディレクトリ構成

公式にバンドルされたプラグインは `src/features/plugins/catalog/` の下にあり、プラグインのプラットフォームごとに 1 つのディレクトリがあります。

```
src/features/plugins/catalog/
  marketplace.json                        ドキュメントのプラグインストアが読む索引
  sites/<site>/site.json                  サイトアダプタ（データとして記述）
  sites/<site>/plugins/<id>/plugin.json   宣言的プラグイン
  sites/<site>/plugins/<id>/style.css     そのプラグインのスタイル
  sites/<site>/plugins/<id>/README.md     何を直すのか、そしてその理由
```

検出は自動で行われます。`catalog/sites/index.ts` が `import.meta.glob` で、すべての `site.json` と `plugin.json` を見つけます。そのため、サイトやプラグインを追加するにはファイルを追加するだけです。編集すべき対応表はありません。

`marketplace.json` は、その対応表ではありません。ドキュメントのプラグインストアが読む索引にすぎません。テストによって検出結果と同期されるため、新しいプラグインはここにもエントリを追加する必要があります。`source` は catalog からの相対パスで、たとえば `sites/deepseek/plugins/reading-width/plugin.json` のように書きます。`sites/gemini/` と `sites/aistudio/` の下にあるプラグインは例外です。これらは Voyager に同梱されるため、`marketplace.json` には含まれません。

プラグインの `matches` は、そのプラグインが置かれているサイトの `matches` の範囲内に収める必要があります。サイトの外にはみ出したプラグインは、ビルドに失敗します。

## 意味的セレクタキー

`site.json` は、固定の語彙に含まれる意味的キーを、サイトごとの CSS セレクタに対応づけます。語彙は `src/features/plugins/sites/semanticKeys.ts` で定義されています。`site.json` で使えるのはこの一覧のキーだけで、未知のキーは拒否されます。

- `userTurn`: ユーザーのメッセージのコンテナ。
- `assistantTurn`: アシスタントのメッセージのコンテナ。
- `thinkingBlock`: アシスタントのターン内にある、推論のセクション。
- `codeBlock`: 描画済みのコードブロック。
- `composer`: ユーザーが入力するプロンプト欄。
- `sidebar`: 会話の一覧、またはナビゲーションのレール。
- `sidePanel`: artifacts や canvas などの副次的なパネル。
- `headerActions`: 会話画面の右上にある操作ボタンのまとまり。
- `scrollContainer`: 会話をスクロールさせる要素。
- `composerRoot`: プロンプト欄と、その操作ボタンを囲むコンテナ。
- `sendButton`: プロンプトを送信するボタン。サイトによっては、入力があるときだけ表示されます。

サイトは、実際に提供できるキーだけを宣言します。プラグインは生のセレクタを書く代わりに、DOM 操作の `target` として `{ "kind": "semantic", "key": "userTurn" }` と書くことでキーを参照します。そのため、サイトのデザインが変わっても、修正は `site.json` の 1 ファイルで済みます。

`conversationIdPattern` はセレクタではなく、`site.json` の別のフィールドです。URL パスに対する正規表現で、最初のキャプチャグループが会話 ID になります。たとえば `^/chat/([^/?#]+)` のように書きます。

## 新しいプラットフォームを追加する

新しいチャットサイトを追加するには、2 つの別々の層があります。

1. **サイトアダプタ** `catalog/sites/<site>/site.json`。Voyager に、そのウェブサイトの認識方法と、ユーザーのターン、アシスタントのターン、入力欄、サイドバー、テーマのマーカーを見つける方法を教えます。
2. `catalog/sites/<site>/plugins/<id>/` の下にある **プラグイン**。そのウェブサイト上で、読み取り幅やレンダリングの修正など、ユーザーが直面する 1 つの問題を解決します。

`site.json` には、`id`（ディレクトリ名と同じ）、`label`、`matches`、`selectors`、`theme`、`brandColor`、`capabilities` と、任意の `conversationIdPattern` および `turnKeyAttributes` が含まれます。`turnKeyAttributes` は、ページが再描画されたときにユーザーのメッセージの識別子を保つ属性の名前を指定します。送信の追跡（フォルダの Activity やタイムラインのタイムスタンプで使われます）は、この属性と `composer`、`userTurn`、`conversationIdPattern` を設定したサイトでのみ動作します。`src/features/plugins/sites/siteAdapterData.ts` の `validateSiteAdapterData` がこれを検証し、`bun run catalog:build` は公開の前にすべてのサイトとプラグインを検証します。

すべてのプラグイン対応プラットフォームはデータとして記述されます。現在のサイトは ChatGPT、Claude、DeepSeek です。Gemini と AI Studio は Voyager のネイティブな画面で、それぞれ独自の `site.json`（`catalog/sites/gemini/`、`catalog/sites/aistudio/`）を持ちます。ただし、これらは拡張機能パッケージに同梱され、リモートカタログには公開されません。5 つのアダプタ（`adapters/gemini.ts`、`aistudio.ts`、`claude.ts`、`chatgpt.ts`、`deepseek.ts`）は、いずれも `site.json` を読み込むだけの 1 行のシェルです。TypeScript ではなく、JSON を編集してください。

公開されるサイトごとのカタログにもサイトのデータが含まれるため、`site.json` のセレクタ修正は、拡張機能のリリースを待たずにユーザーに届きます。ただし、まったく新しいサイトには、やはり拡張機能の中に含める必要があります。ホスト権限とコンテンツスクリプトの登録が、パッケージに組み込まれているためです。

DeepSeek のような新しいプラットフォームを追加する場合は、アダプタの作業をプラットフォームとの契約に絞ってください。`site.json`、必要なセレクタのテスト、そして対応内容を説明するための最低限のドキュメントを、1 つの完全な変更にまとめます。サイトのレジストリは、ファイル自体から新しいアダプタを読み込むので、登録リストを編集する必要はありません。プラグインごとに新しいサイトを追加しないでください。

アダプタが承認されたあとは、後続のプラグインを、独立した焦点の絞られた変更として提出できます。複数の変更が互いに依存している場合は、スタックされた PR の連鎖が役立ちます。後続のブランチは直前のブランチを基にし、各 PR には、そのPR独自の増分の機能だけが表示されます。それでも連鎖全体で同じスコープのルールに従ってください。PR ごとに、明確なユーザー目標を 1 つだけ持ち、必要なテストと後片付けを含めます。

サイトの対応に、モデル API との連携は必要ありません。新しいプラットフォームのために、静的なコンテンツスクリプトや必須のホスト権限を追加しないでください。プラグインだけのサイトには、既存のオプション権限と動的な登録の仕組みを使ってください。

オプション権限と動的な登録の仕組みは、ブラウザのバージョンに依存します。Chrome と Edge は、この拡張機能が使っている仕組みに対応しています。Firefox はオプションのホスト権限に バージョン 128 以降を必要とし、Safari は動的なコンテンツスクリプトの登録にバージョン 16.4 以降を必要とします。対応しているより古いブラウザでは、必要な API が永続的な許可を提供できないため、カスタムサイトでプラグインを有効にできなくても、それは正しい動作です。メンテナーの承認なしに、広い静的なホスト権限を追加して回避しないでください。

## プラグインの範囲

プラグインは、プラットフォームで機械的に分けるのではなく、ユーザーが解決したい問題によって範囲を決めてください。

カタログのプラグインは 1 つのサイトフォルダに置かれ、その `matches` はすべて、そのフォルダの `site.json` がカバーしている必要があります（そうでなければ `bun run plugin:check` が失敗します）。そのため、1 つのプラグインで Claude と ChatGPT の両方を対象にすることはできません。読み取り幅、ページのナビゲーション、コードブロックのレイアウトのように、同じ機能が複数のプラットフォームに当てはまる場合は、サイトフォルダごとに 1 つのプラグインを提供してください（例：`sites/claude/plugins/reading-width` と `sites/chatgpt/plugins/reading-width`）。そして、名前、設定、説明をそろえてください。

プラットフォームごとに設定、DOM のロジック、ユーザーに表示する文言が大きく異なる場合は、別々のプラグインにしたほうが分かりやすくなります。「何でもできる」ようにするために、無関係な動作を 1 つのプラグインに詰め込まないでください。1 つのプラグインは、1 つの明確な問題を解決するべきです。

簡単な判断基準は次のとおりです。

- 同じユーザー目標で、同じ設定、違うのはセレクタだけ：サイトフォルダごとに 1 つのプラグインを作り、名前と設定をそろえる。
- 同じテーマでも、プラットフォームごとの動作が大きく違う：分けてもよいが、名前と説明は関連付ける。
- 目標が異なる：統合しない。

## 重複するプラグインを避ける

提出する前に、プラグインマーケットと既存の公式プラグインを確認してください。すでによいプラグインがあれば、似たものを新しく作るのではなく、既存のプラグインを改善してください。

重複するプラグインが受け入れられるのは、次のような明確な改善がある場合だけです。

- 元のプラグインが対応していない、重要なプラットフォームをサポートする。
- 元のプラグインでは解決できない互換性の問題を修正する。
- パフォーマンス、アクセシビリティ、保守性が明らかに優れている。
- 名前を変えたり、少しスタイルを変えたりしただけではなく、意味のある別の体験を提供する。

これにより、マーケットプレイスが整理され、ユーザーは選びやすくなります。

## 最小の例

空のディレクトリから始めるのではなく、雛形から始めてください。`bun run plugin:new <id-segment> --site <site>` を実行すると、`catalog/sites/<site>/plugins/<id-segment>/` が作られ、`plugin.json`、`style.css`、`README.md` が含まれ、`marketplace.json` にもエントリが追記されます。生成されるのは出発点にすぎず、承認を意味しません。記入するマニフェストは、次の形式になります。

```json
{
  "$schema": "https://voyager.nagi.fun/plugin.schema.json",
  "id": "your-name.example-plugin",
  "name": "Example Plugin",
  "version": "1.0.0",
  "description": "A short description of what this plugin improves.",
  "author": "your-name",
  "category": "readability",
  "license": "MIT",
  "engine": ">=1.0.0",
  "tier": "declarative",
  "matches": ["https://claude.ai/*"],
  "contributes": {
    "styles": [{ "file": "style.css" }],
    "domOps": [
      {
        "op": "addClass",
        "target": "body",
        "className": "gv-plugin-example"
      }
    ]
  }
}
```

`$schema` の行は任意で、エディタ専用です。マニフェストの JSON Schema を指すため、入力中にファイルが検証され、補完も効くようになります。`site.json` の Schema は `https://voyager.nagi.fun/site.schema.json` にあります。

`style.css` では通常の CSS を使えますが、プラグインのスタイルは自分の `gv-plugin-*` クラスの下にスコープしてください。

```css
.gv-plugin-example .some-target {
  max-width: 880px;
}
```

## マニフェストの注意点

- `id` には、`your-name.reading-width` のように、逆ドメイン形式または作者のプレフィックスを付けて、衝突を避けます。
- `matches` はできるだけ狭くしてください。プラグインが本当に動作する必要のあるウェブサイトだけに一致させます。
- プラグインの `matches` に複数のホストを書けるのは、そのサイトの `site.json` がそのすべてをカバーしている場合だけです（例：chatgpt.com と chat.openai.com）。別のサイトを対象にするには、そのサイトのフォルダにプラグインを追加してください。
- `category` の推奨値は、`render-fix`、`theme`、`layout`、`readability`、`productivity`、`integration`、`other` です。
- `engine` には、必要なプラグインエンジンのバージョンを設定してください。公式プラグインを例として参照できます。
- 可能であれば、中国語、英語、そのほかの一般的な言語の `i18n` を追加してください。

## CSS とリソースの制限

宣言的プラグインは、信頼されていない入力として検証されます。そのため、リソースは自己完結させてください。

- `@import` を使わない。
- リモートの画像、外部フォント、リモートの CSS を参照しない。
- 通常の CSS、カスタムプロパティ、Voyager の設定値の置換は使えます。
- プラグインのクラスには `gv-plugin-` の接頭辞を付け、ホストのウェブサイトや Voyager 自体にスタイルが漏れないようにします。

プラグインに設定が必要な場合は、できれば数値の設定から始めてください。たとえば読み取り幅のプラグインは、設定の値を CSS 変数に書き込み、CSS 側でその変数を使えます。

## DOM 操作の境界

宣言的プラグインが現在サポートしているのは、次の操作です。

- `addClass`: 対象の要素にクラスを追加する。
- `setAttribute`: 属性を設定する。
- `setStyle`: インラインスタイルまたは CSS 変数を設定する。値の末尾に `!important` を付けると、その優先度で適用されます。古い Voyager ではこの値が破棄されるため、プラグインがこれに依存する場合は `engine` を `>=1.9.0` にしてください。`margin` などのショートハンドは、ロングハンドごとに追跡されます。そのため、あるプラグインをオフにしても、別のプラグインの `margin-top` が消えることはありません。
- `hide`: 対象の要素を非表示にする。

対象には、CSS セレクタか、上で説明した意味的キーを指定できます。意味的キーは `{ "kind": "semantic", "key": "userTurn" }` と書きます。意味的キーは通常より安定していますが、現在のサイトアダプタがそのキーを宣言している必要があります。

宣言的な操作は、取り消し可能で、何度実行しても安全でなければなりません。一度きりのページの状態に依存せず、ページの DOM が決して変わらないとも仮定しないでください。

### プリミティブ

CSS と取り消し可能な DOM 編集だけでは表現できない動作もあります。プリミティブとは、Voyager に同梱されているファーストパーティのコードのことで、マニフェストは `native` 操作を通して名前で呼び出せます。

```json
{
  "engine": ">=1.3.0",
  "requires": { "handlers": ["formulaCopy"] },
  "contributes": {
    "domOps": [{ "op": "native", "handler": "formulaCopy", "params": {} }]
  }
}
```

マニフェストは、プリミティブを選んで設定するだけです。ロジックを提供することはありません。`params` は、実行される前にそのプリミティブが検証します。

プリミティブを使うプラグインには、次の 2 つのルールが適用されます。

- プラグインがマッチするすべてのサイトが、そのプリミティブが読み取る意味的キーを宣言していること。たとえば `mermaid` は `assistantTurn` と `codeBlock` を読み取ります。`requires.handlers` は省略できます。`native` 操作が、すでにそのプリミティブを指定しているためです。
- `engine` は、そのプリミティブが最初に含まれたエンジンバージョン以上であること。`formulaCopy` はエンジン 1.3.0 で追加されたので、それを使うプラグインは `">=1.3.0"` と宣言します。これより低い範囲を指定すると `bun run catalog:build` が失敗します。古い Voyager では、アップデートを促す代わりに、ハンドラが見つからないと報告してしまうためです。

プリミティブは増えていくだけです。新しいパラメータは必ず任意にし、互換性を壊す変更は新しい名前で提供します。

動作を変えたプラグインには、1 行の `changelog` を付けることもできます。ポップアップがバージョン番号の横に表示します。翻訳は `name` と `description` の隣の `i18n.<locale>.changelog` に書きます。

## 通常のプラグインに向かない場合

JavaScript の実行、ネットワークリクエストの横取り、Voyager の内部データの読み書き、複雑な実行時のロジックが必要な機能は、通常の宣言的プラグインには向いていません。

まず Issue を開いて、必要な機能を説明してください。本当に内蔵の機能が必要な場合は、Formula Copy のように、builtin/native プラグインとして Voyager 本体に実装することを検討します。

## PR を開く前に

`bun run plugin:check <プラグインディレクトリ>` を実行し、その出力を PR に貼り付けてください。このチェックは、マニフェストと CSS から、サイトの範囲、プリミティブ、意味的セレクタキー、10 言語のロケール、README まで、問題をすべて一度に報告します。CI も、すべての同梱プラグインに対して同じチェックを実行します。

- プラグインは既定で無効になっており、ユーザーが自分で有効にします。
- ほぼ同一の既存プラグインがないことを確認しました。ある場合は、既存のプラグインを先に改善しました。
- 対象のウェブサイトで、ライトテーマとダークテーマの両方をテストしました。
- `matches` が無関係なサイトを含んでいません。
- リモートのリソースを使っていません。
- プラグインのディレクトリに、`plugin.json`、必要な CSS ファイル、短い README があります。
- 公式プラグインの場合、ディレクトリが `catalog/sites/<site>/plugins/<id>/` にあり、`matches` がサイトの `matches` の範囲内にあり、`catalog/marketplace.json` に登録されています（Gemini と AI Studio のプラグインは Voyager に同梱されるため、登録は不要です）。
- PR に、テストページ、スクリーンショットまたは録画、影響を受けるページの領域が記載されています。

シンプルで、焦点が絞られていて、取り消し可能な状態を保ってください。明確な問題を 1 つだけ解決するプラグインは、マージも保守もはるかに容易です。
